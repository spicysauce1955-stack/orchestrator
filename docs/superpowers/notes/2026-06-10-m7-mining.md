# M7 — knowledge mining (2026-06-10)

Branch `m7-knowledge-mining`, plan `docs/superpowers/plans/2026-06-10-m7-knowledge-mining.md`,
TDD, **334 tests green** (was 319), ruff clean. Implements spec §8.1: capture →

auditor-gated `mcp__knowledge__write`.

## What landed

- `orchestrator/knowledge/miner.py` — `mine(span_db, min_runs=2)` over the M6d
  span store, three deterministic detectors (no LLM), each requiring evidence in
  ≥ min_runs distinct runs (trace→run via root `run` spans, multi-trace safe):
  - `recurring_step_failure` — `step` spans with `step.is_error`.
  - `repeated_rejection` — `message` spans `msg.kind="verdict"` grouped by
    `msg.to`; surfaces the latest feedback body (truncated 200 chars).
  - `recurring_tool_failure` — failed `tool_call` spans + errored `mcp.call`
    spans (subject `mcp:<tool>`, enabled by the cleanup track's MCP spans).
- `write_candidates` → regenerated `candidates.md` with an UNVETTED header
  naming the auditor's vetting duty; sorted most-evidenced first.
- `orch mine [--repo] [--min-runs N] [--out PATH]` — prints candidates and
  writes `<repo>/.orchestrator/knowledge/candidates.md`.
- Example: `knowledge/candidates.yaml` source + auditor read grant
  (`read: [repo-conventions, lessons, candidates]`) — the closed loop is
  mine → candidates.md → auditor searches it via the existing knowledge MCP →
  vets → gated write to lessons.md (seam-tested in `test_miner.py`).

## Deferred / follow-ups

- LLM-assisted candidate summarization (dedup/cluster across kinds) — the
  detectors are deliberately deterministic in M7.
- Auto-mining after `orch run` (currently an explicit offline command, per spec
  "offline miner").
- An `audit` step prompt template that explicitly instructs candidate vetting —
  the grant exists; prompt wording is pipeline-author territory.
- Verdict messages don't carry the rejected step's run attempt; candidates cite
  runs, not attempts.
