# M9 — best-of-n fan-out with judge-based selection (2026-06-10)

Branch `m9-best-of-n`, plan `docs/superpowers/plans/2026-06-10-m9-best-of-n.md`,
TDD, **364 tests green** (was 347), ruff clean. Implements spec §4 / §14 #5:
N candidates, one accountable read-only judge — our governed analog of swarm
consensus voting. This closes the last planned post-MVP milestone (M7–M9 all
shipped).

## What landed

- **Authoring:** `Step.best_of` (2–5; cap = budget sanity) + `Step.judge`
  (role name). Schema validation: best_of⇔judge pairing, agent steps only.
  Loader cross-validation: judge role must exist and be **read-only**
  (writer≠judge enforced at config time).
- **Executor-level fan-out** (`run_best_of_step` in `runtime/executors.py`):
  the graph stays linear (one node → M6d one-trace-per-run invariant holds; no
  LangGraph parallel-state reducers). Each candidate = a full `run_agent_step`
  under a cloned id `<id>.cand<k>` — own worktree/branch (`orch/<run>/<id>.cand<k>/<n>`),
  own success_criteria/retry. The judge = one more read-only agent step
  `<id>.judge` whose prompt carries each qualifying candidate's diff (truncated
  4k) and whose `output_schema` is `{winner: enum[<qualifiers>]}` — its artifact
  IS the selection verdict.
- **Selection semantics:** errored candidates disqualified; 0 qualifiers →
  error artifact; exactly 1 → wins without judge cost; judge error/unparseable
  → **step error, never a silent fallback** (the benchmark's "review loop
  silently always-proceeds" lesson, bug #4). Winner artifact is re-recorded
  under the step id (diff flows to merge; `{{step.diff}}`/`{{step.output}}`
  reference the winner).
- **Cost accounting:** candidate/judge artifacts recorded normally (run total
  correct); the final winner-clone is written directly with cost = sum so the
  total isn't double-counted. Merge collects only `pipeline.steps` ids, so
  `.cand<k>`/`.judge` diffs can never leak into a PR.
- **Dispatch:** scheduler resolves the judge's harness via the registry (judge
  may run on a different harness than candidates); CLI `--only` handles best-of
  steps too. on_reject loop-backs into a best-of step work: attempts are
  counted on the step id and relayed reviewer feedback is re-seeded to every
  candidate.
- **Fixtures:** fake harness gained `winner` (judge) and `implement`
  (state-numbered candidate variants) prompt routes; shared scripts dir gained
  `winner.ndjson` only — existing routing behavior preserved.
- Example `best-of.yaml` (classify → implement best_of:2 judge:reviewer →
  merge) compiles; spans carry `bestof.n` / `bestof.winner`.

## Deferred / follow-ups

- **Candidates run sequentially** — concurrent `git worktree add` lock-safety
  unproven; switch to `asyncio.gather` after proving it (worktrees are
  otherwise independent).
- Judge rubric is a fixed prompt (correctness/robustness); no scoring config.
- No candidate-diversity mechanism (different models/temperatures per
  candidate would need per-candidate role overrides).
- **Premise check (benchmark findings):** on 6/6 solvable bespoke tasks the
  base agent never erred — best-of, like the review loop, only pays when
  candidates diverge. The un-hinted / multi-component benchmark experiment
  remains the way to measure whether best-of buys real pass@1.
